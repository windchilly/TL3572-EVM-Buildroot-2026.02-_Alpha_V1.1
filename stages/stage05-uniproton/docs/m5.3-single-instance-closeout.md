## 2. 最终硬件与内存定案

| 项目 | 最终值 |
|---|---|
| Linux CPU | CPU0～CPU6 online |
| UniProton CPU | CPU7，MPIDR `0x201`，A73 |
| 中断控制器 | GIC-400 / GICv2，GICD `0x2a601000`，GICC `0x2a602000` |
| UniProton tick | CNTV PPI11，对应 GIC hwirq 27 |
| MCS notify | GIC hwirq 8；Linux 映射 virq 9，名称 `MCS IPI` |
| MCS IPI 目标 | 只投递 Linux CPU0 |
| 保留内存 | `0x7a000000..0x7dffffff`，64 MiB，no-map |
| CPU7 OpenAMP 池 | `0x7a0e0000..0x7a0fffff`，128 KiB |
| 日志预留 | `0x7c000000..0x7c1fffff`，2 MiB |
| ELF LOAD/入口 | `0x7c200000`，单 LOAD 段 MemSz `0xd2c90` |
| MMU 表区 | `0x7ca00000..0x7d1fffff`，8 MiB |

保留内存从早期的 `0x134000000` 下移，是因为当前 micad/MCS vring 地址链存在
32 位截断；高于 4 GiB 的地址会变成 `0x340e0000` 并落入 Linux 普通内存。
最终低地址布局同时把 CPU7 的 128 KiB MCS 共享池与固件 LOAD 段彻底分开。

> 2026-09-21 硬件标识复核：早期规划把 cluster2 记作 A72；实机 CPU6/CPU7
> MIDR 为 `0x411fd090`，part `0xd09`，Linux `cputype.h` 对应 Cortex-A73，现已更正。

## 3. 关键问题与最终修复

### 3.1 SGI 映射

调试阶段曾把 `/proc/interrupts` 左侧的 Linux IRQ 号 9误认为硬件 SGI9。
最终内核修改为连续分配 SGI0～SGI8：Linux 自用 SGI0～SGI7，导出 SGI8
对应的 Linux virq 给 `mcs_km`。板上最终证据为：

```text
  9: ... GICv2   8 Edge      MCS IPI
```

因此硬件中断号是 **SGI8**，Linux virq 才是 9。UniProton 发送路径已恢复为
单一 CPU0 target，调试用“all-other CPU”广播已删除。

### 3.2 GICv2 与 Timer

- 通用 GICv2 代码原先仍使用 Raspberry Pi 地址，RK3572 构建现显式覆盖 GICD/GICC；
- CNTV 使用 PPI11/hwirq27，而不是早期假设的 hwirq30；
- 异常向量、VBAR 和中断路径经诊断后恢复标准实现，所有 `UP7-*`、
  `[openamp-diag]` 与同步异常临时打印均已移除。

### 3.3 可重复 stop/start

UniProton 打开 `CONFIG_OS_OPTION_POWEROFF=y`，补齐 PSCI 下电声明；停止实例后
CPU7 真正下电，随后可再次由 Linux/TF-A 拉起。最终 1,000 轮测试每轮均执行：

```text
mcsctl stop up0
mcsctl start up0
等待 up0=Running 且 /dev/ttyRPMSG0 出现
发送并校验 451 字节 RPMsg TTY 回显
```

旧生产清理版结果为 `1000/1000 PASS`（745.871s）；删除最后两条启动诊断、
修正依赖补丁与 fail-fast 后，对最终 ELF 重新执行同样 1,000 轮，结果仍为
`1000/1000 PASS`（746.102s）。

### 3.4 RPMsg 大包和接收队列

- Linux MCS `micad` 的 RPMsg TTY 缓冲从 256 改为完整 payload 496 字节；
- UniProton TTY 接收由单槽改为深度 8 的 held-buffer 队列；
- 队列元数据使用 `PRT_HwiLock/Restore` 保护；
- 删除 `data[len] = '\0'` 越界写，格式化改为有界 `%.*s`；
- UniProton 回复缓冲固定为 496 字节并对 `snprintf` 返回长度限幅。

最终 451 字节输入加 `Hello, UniProton! Recv: ` 前后缀形成 478 字节单帧响应。
最终 ELF 测试结果：10,000 次顺序回显全部通过，接收 `4,780,000` 字节，
用时 `6.039s`。

## 4. 构建正式化

### 4.1 Linux 与 MCS

- 内核补丁：`0001-arm64-smp-reserve-SGI-for-mcs-km.patch`；
- MCS 补丁：`0001-mcs-rpmsg-tty-full-payload.patch`；

- `bitbake mcs-linux -c cleansstate && bitbake mcs-linux` 通过；

- `bitbake tl3572-openeuler-mcs-image` 的 2920 个任务通过。

首次整镜像构建发现 sstate 复用了旧 micad；随后用正式 patch + cleansstate 重建，
最终 rootfs 内的 stripped micad Build ID 与 work 目录新二进制一致。

最终 UniProton 重编时进一步修正：

- `build_app.sh` 与 `build_openamp.sh` 加 `set -e`，消除依赖失败后继续链接旧库/旧 ELF；
- libmetal 持久补丁的新增文件 hunk 行数由 73 修正为 79；
- `__metal_mutex_is_acquired()` 修复进入持久补丁源，重新 clone libmetal 后仍生效；

- 新固件进入 Yocto 层后再次构建镜像，2920 任务全部成功，其中 9 项实际重跑。

最终构建仍有不阻塞本阶段的上游/通用警告：libmetal `metal_assert` 空体、OpenAMP
局部变量未使用、litelibc endian 运算括号、proxy 恒假地址判断及 ELF RWX LOAD 段。

### 4.2 自动启动

最终 rootfs 包含：

- `mcs-km-load.service`：在 micad 前加载 `/lib/modules/mcs_km.ko`；

`systemctl --failed` 为 0。
