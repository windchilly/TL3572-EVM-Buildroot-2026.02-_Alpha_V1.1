## 1. 分配原则

- 按**物理控制器**确定唯一所有者，而不是按 Linux 设备名或同一控制器的若干通道拆分。分给 UniProton 的外设必须由对应实例直接驱动寄存器和中断；RPMsg 只用于管理、诊断和测试协调，不作为该外设的数据或 I/O 代理。
- 直驱前须查清控制器、收发器方向控制、pinmux、时钟、复位、IRQ、DMA、共享 GPIO/I2C 依赖，并在 Linux 设备树中释放完整控制器及相关资源。仅停止 Linux 用户态程序不等于移交所有权。
- 启动、恢复、调试、电源管理和至少一路管理网络保留给 openEuler。两个 UniProton 不共用物理控制器，也不直接驱动同一个输出。
- 只规划 M7.0 的两个独立工控域：**UP1 负责模拟量采集和现场通信 A，UP2 负责现场总线/以太网通信 B**。两者可以运行不同业务，不要求相同输入、相同算法、主备或表决；不把后续阶段的实例数和架构当成本轮约束。
- 不改板、不新增专属 I/O 模块，并保留一路原生千兆网口给 openEuler。UP1/UP2 的 CAN、RS-485、RS-232 发送测试只用隔离的非执行器对端；在现场协议、输出安全态和联锁条件未定义前，不向真实执行机构发送控制命令。
- 已确认的 ETH2 直驱口径：**启动阶段允许对 PHY 复位做一次性初始化；UP2 启动后独立控制 GMAC1、MDIO、PHY 链路和收发，Linux 不再运行时代管或改动该 PHY 复位脚**。这是需求定义，不代表当前镜像已实现；若不能仅靠 UP2 完成运行时恢复，ETH2 不移交。
- 正式运行时 UART4/8 分别用于 UP1/UP2 的 RS-232 工控通信，不占作常驻调试口。UP 启动进度和日志通过各自的保留内存日志环、独立 RPMsg 诊断通道及 Linux 收集服务监视；诊断通道不代理工控外设数据。开发期可临时把 UART4/8 切换为各自的物理调试口，但该模式下相应 RS-232 工控功能不可同时验收。

|---|---|---|

## 2. 计算、内存与通信资源

UP1=现有 UP-A，UP2=现有 UP-B。前五行是已验收的 M6 双实例基线；外设相关行是 M7.0 新增目标，CAN1/3 和 UART4/8 已有临时直驱切片，其余未完成，持久所有权均未移交。CPU 拓扑为 CPU0～5=A53、CPU6～7=A73；M7.0 保持 M6 的双实例布局，不迁核、不增加 SGI10。

| 资源 | openEuler | UP1 | UP2 |
|---|---|---|---|
| CPU | CPU0～3、CPU6～7 | CPU4 / MPIDR `0x100` | CPU5 / MPIDR `0x101` |
| 固件入口 | 加载与管理两实例 | `0x7b200000` | `0x7c200000` |
| MMU/保护区基址 | 保留，不作普通 Linux 内存 | `0x7ba00000` | `0x7ca00000` |
| OpenAMP 共享池 | 分别连接，不交叉映射 | `0x7a080000..0x7a09ffff` | `0x7a0a0000..0x7a0bffff` |
| 通知中断 | Linux 自身 SGI0～7；MCS 管理路由 | SGI8 | SGI9 |
| 物理 I/O 约束 | 管理接口、I2C1/U21/U22、ETH1/ETH3 | 自己的 CAN/UART/SARADC | 自己的 CAN/UART、候选 GMAC1/MDIO/PHY |
| 跨 OS 通道 | MICA/RPMsg 只作启动、状态、诊断与测试协调 | 不经 Linux 代理本域外设数据 | 不经 Linux 代理本域外设数据 |

MCS 总保留内存仍为 `0x7a000000..0x7dffffff`（64 MiB），不得作为 Linux 普通内存重新分配。`0x7a000000..0x7affffff` 是主控共享区；UP1 的 16 MiB 固件切片为 `0x7b000000..0x7bffffff`，UP2 为 `0x7c000000..0x7cffffff`。`0x7d000000..0x7dffffff` 保持预留，不在 M7.0 运行第三实例，也不借给任一外设作未经审计的 DMA 缓冲区。固件入口是切片内的加载地址，MMU/保护区基址不是额外独立的物理内存。RPMsg 的两个 128 KiB 池只承载控制、状态、诊断，不承载分给 UP 的物理 I/O 数据路径。

### 2.1 共享平台资源的所有权边界

| 资源/依赖 | M7.0 责任方 | 分界与必须验证的动作 |
|---|---|
| 启动链、固件加载、MICA 生命周期、镜像回退 | openEuler 与既有启动固件；UP1/UP2 为被加载方 | 保留 UART0、存储和 ETH1 救援入口；记录加载顺序，M6 `AutoBoot=no` 基线先不改。 |
| GIC 全局配置与 SGI 路由 | Linux/MCS 管理全局；UP1 用 SGI8，UP2 用 SGI9 | 外设 SPI/PPI 按控制器单独路由给唯一所有者；实际 IRQ 号以运行中 DT/寄存器核对，不照搬静态猜测；不能让 Linux 驱动同时收同一 IRQ。 |
| pinctrl/GRF、CRU 时钟与复位 | 启动初始化由 Linux/固件编排；外设运行时由相应所有者独占相关控制位 | 为每个 UP 控制器核对 pinmux、clock gate、reset、pinctrl 与电源域；若控制寄存器同时服务 Linux 外设，须有可验证的位级边界和无冲突写入，不能把整块共享寄存器粗暴交给任一 UP。 |

| CPU 时钟/频率、电源域、系统热管理 | openEuler 管理系统策略 | Linux 调频、休眠、复位或电源域操作不得使 UP 外设失效；在并发和故障测试中记录运行时频率与电源状态。 |
| I2C1 及 XL9555 U21/U22、RTC/摄像头支路 | openEuler 独占运行时 I2C1 | U21 P00/P01 分别关联 ETH1/ETH2 PHY reset；ETH2 的 P01 仅允许启动阶段一次性初始化，之后 Linux 不再写该脚；U22 的 DI/DO、看门狗/FPGA 控制和 USB Hub reset 不拆分给 UP。 |
| RS-485 收发方向 GPIO/RTS 与可能共享的 GPIO bank | 对应 UART 的 UP1 或 UP2；其他 bank 位仍按实际外设所有者 | 本轮采用UART MCR/RTSN手动换向，UP自主RTS mux，不写GPIO bank；自动RTS/CTS尚未验收。若将来改GPIO须先做bank并发审计，不能由Linux运行时代管。 |
| 管理与诊断平面 | openEuler + 各 UP 的 RPMsg 端点 | 仅传启停、健康、版本、测试指令与结果；不能用 Linux SocketCAN、串口、ADC 或网卡服务替代 UP 对已分配控制器的直驱。 |

上述共享寄存器、IRQ、DMA 与 GPIO 的具体地址/编号尚须从最终生效设备树和实机验证后填入逐控制器台账；本需求稿不把未核实的地址写成已验收事实。

|---|---|---|---|

候选日志空间是 UP1 切片前 2 MiB `0x7b000000..0x7b1fffff` 和 UP2 切片前 2 MiB `0x7c000000..0x7c1fffff`，须先核对最终链接脚本、保留区占用和缓存属性，再增加 UP 的 MMU 映射及 Linux 受控只读映射。不得挤占各自 128 KiB OpenAMP 池或把日志写入另一实例切片。日志环需有启动序号、顺序号、长度/校验、溢出计数和明确的写入顺序；实时任务与中断不能为等待 Linux 读日志而阻塞。Linux 整机掉电或崩溃时，RPMsg 监视不可用，未持久化的内存日志也不能保证留存；极早期故障仍需开发期物理串口或 JTAG 定位。

M6 的 UP 板级配置定义并映射 UART0 `0x2c130000`；M7 首切片已将 `PRT_Printf`/`printf` 改写到保留内存环，并移除该 UART0 MMIO 映射，实机读到 CPU 入口至 RPMsg 就绪的记录。M6 已验证的 RPMsg tty/rpc/umt 端点仍**不等于**独立 RPMsg 日志端点、心跳和异常留存完成；当前 Linux 读取依赖 root `/dev/mem`。详见 [首轮实机记录](../tests/board/m7-observability-bringup-20260928.md)。

## 3. 评估板全接口的拟定归属

“openEuler”表示 Linux 直接拥有并测试；“预留”表示本轮由 Linux 保持所有权或禁用，不允许其他 OS 同时访问。外设名称以板卡丝印为准，不能直接把 `/dev/ttyS*`、`can*` 或动态 GPIO 编号当作稳定的物理映射。

| 评估板接口/资源 | M7.0 拟定物理所有者 | 功能定位与边界 |
|---|---|---|
| eMMC、UFS、Micro SD、M.2 Key M/NVMe | openEuler | 启动、程序、日志、升级与恢复；选件缺席记 `N/A`。DDR 的普通区由 Linux 管理，MCS 保留区按第 2 节分给 UP1/UP2，不能把整片 DDR 算作 Linux 独占。 |
| ETH1 / 原生 RGMII 千兆（原理图对应 GMAC0） | openEuler | 主有线管理、升级和恢复通道；本阶段不移交。 |
| ETH2 / 原生 RGMII 千兆（原理图对应 GMAC1） | UP2 直驱目标，软件可行性待验证 | 工控以太网 B；按已确认口径，启动阶段可一次性释放 PHY reset，运行时由 UP2 独立控制 GMAC/MDIO/PHY；若不能自行恢复链路则仍归 openEuler。 |

这是一版**候选分配**，不是已生效的设备树配置。板卡规格书给出的数量为 3 路 Ethernet、4 路 CAN FD、2 路 RS-485、2 路 RS-232、4DI/4DO、6 路 ADC，另有 USB、无线、显示、摄像头、音频和扩展接口。厂商测试手册给出 Linux/Buildroot 的接口验证方法，不能直接当作当前 openEuler 镜像的实测结果。

特别注意：原理图第 10、25 页显示 DI1～4/DO1～4 均接到 XL9555 U22；U22 还连接外部看门狗配置、FPGA 控制信号和 USB Hub 复位，并与负责 RGMII PHY 复位的另一颗 XL9555、RTC/摄像头等共用 I2C1。**不改板时不能把 U22 独占交给 UP2 而保持 Linux 继续使用 I2C1**，所以本阶段明确留给 openEuler。原理图还注明 `SARADC_IN6` 用于 SOM DDR 型号识别，上电时不得外接驱动信号。

ETH2 也不是只禁用 Linux `gmac1` 节点即可直通。当前板级 DTS 的 GMAC1 PHY 复位使用 Linux I2C1 上另一颗 XL9555 的 P01。用户已接受启动阶段一次性释放复位作为直驱边界；实施时须记录负责该动作的启动组件、时序和最终引脚状态，确认 Linux 在 UP2 启动后不再触碰 P01，并验证 UP2 可通过 MDIO 独立完成运行时软复位和链路恢复。**若仍需 Linux 运行时替 UP2 控制复位，该方案不满足已确认的直驱要求**，ETH2 不得移交。当前 UniProton 基线没有 RK3572 GMAC/MDIO/PHY 驱动，需补齐 DMA 一致性、cache、IRQ 与网络协议路径后再测，不可把 RPMsg 转发或 Linux Socket 当作直驱。

实施期间 ETH1 始终由 openEuler 持有；保留 UART0 救援及镜像回退。只有 ETH2 的 PHY 复位路径和 UP2 直驱驱动在不改板条件下验收通过，才移交 ETH2。ETH3 作为备用单独验证，但不作为释放 ETH1 的前提。

厂商手册板号UART1/2反向对应SoC UART2/1，方向GPIO78/27分别为GPIO2_B6/GPIO0_D3。
2026-10-09核验CA-IS3082 RE/DE同接RTSN，并完成UP MCR0=TX/2=RX手动换向五轮，
数据只在各UP ISR收发；GPIO编号只用于核对，不通过Linux GPIO或共享bank读改写控制方向。
自动RTS/CTS、持久引脚所有权和冷启动未验收；成对测试不能单独解决手册丝印与原理图网名编号差异。

## 5. M7.0 仍需确认的条件

1. 按当前规划，UP1 是模拟量/现场通信 A，UP2 是现场总线/以太网通信 B；需确定各自连接的传感器、隔离测试对端、CAN ID、串口协议和实际控制任务。本阶段不讨论主备或表决，DI/DO 仍是 Linux 系统接口。
2. 不改板条件下，DI/DO 由 openEuler 持有，不列为 UP2 直驱目标。ETH2 的一次性 PHY reset 例外已获确认，但软件可行性尚未实测；失败即保留 Linux 所有。UP1 独占 SARADC 则需处理板上按键及 DDR 识别引脚限制。
3. ETH2 是普通工业以太网还是需要 EtherCAT/其他实时协议、各通道的周期、最大允许抖动/超时、失效安全输出、可用仪器和选配硬件，都需要给出数值或测试条件，才能把第 4 节变成可判定的验收标准。
