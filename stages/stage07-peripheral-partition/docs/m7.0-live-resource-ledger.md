# M7.0 实机资源台账：迁移前基线

采集对象：`192.168.2.141`，2026-09-28 的 M6 openEuler 运行镜像。原始生效设备树见 [`tl3572-live-m6-20260928.dtb`](../tests/board/tl3572-live-m6-20260928.dtb)（SHA-256 `39bfcc92d430b88e8f900506b6103d14184d7ef25bf468f903cd88479ba3ebba`）及由 `dtc -I dtb -O dts` 生成的 [DTS](../tests/board/tl3572-live-m6-20260928.dts)。下表 IRQ 数字是设备树 GIC SPI 硬件号，不是 Linux 动态 IRQ 号。表中“目标所有者”是本阶段规划，**当前尚未移交**。

|---|---:|---:|---|---|

| I2C1 / `i2c@2c030000` | `0x2c030000` | 90 | Linux，含 XL9555 `0x20`/`0x21` | openEuler；`0x20` 的 P01 仅允许启动阶段一次性释放 ETH2 PHY reset |

GMAC1 生效 DT 的 `snps,reset-gpio = <0xd6 0x01 0x01>` 指向 I2C1 上 `gpio@20`（XL9555 U21）的 P01，低有效。UP2 启动后 Linux 不得再次运行时切换 P01；若 UP2 无法通过 MDIO 独立恢复链路，则 ETH2 保留 Linux 所有权。`gpio@21` 是另一颗 XL9555 U22，关联板载 DI/DO 与 USB Hub reset，仍归 Linux。

当前 `/sys/bus/iio/devices/iio:device0/` 暴露 `in_voltage0_raw` 至 `in_voltage7_raw`；这不等于评估板向外提供 8 路安全可测输入。尤其 `SARADC_IN6` 还有 SOM DDR 型号识别依赖；移交前要确认 Linux `adc-keys1/2` 行为与上电识别不会被破坏。

2026-09-28 接线实测确认板载 CAN FD1 对应 Linux `can1` / CAN1（`0x2ab10000`，SPI 153），CAN FD3 对应 `can3` / CAN3（`0x2ab30000`，SPI 155）。FD1 ↔ FD3 经典 CAN 每接口累计收发各 10,640 帧，三轮 stop/start 后错误、丢包和 bus-off 均为 0。当前 Linux `rk3576_can` 拒绝 `fd on` 且接口 MTU 不能切换为 72，故 CAN FD 数据相位未测；FD2、FD4 的物理丝印映射也仍待逐口接线确认。完整记录见 [CAN 物理基线测试](../tests/board/can-20260928/README.md)。

同日完成 UP 侧首个寄存器直驱切片：Linux 在测试窗口解绑 CAN1/CAN3，UP1 与 UP2 以轮询方式直接访问各自 MMIO，三轮各完成 1,000 次请求/响应，双方每轮 TX/RX=1000/1000、TXERR/RXERR=0；每轮均停止 UP 并重绑 Linux，`micad` 未重启。详情见 [UP1/UP2 CAN 直驱记录](../tests/board/can-direct-20260928/README.md)。该切片仍借用 Linux 解绑前完成的 pinctrl/clock/reset 准备，只覆盖经典 CAN 数据面，不包含 SPI 153/155 中断、CAN FD/BRS、FD2/FD4 或上电自主初始化，故本台账仍把 CAN 最终所有权标为“目标”。

外设迁移需成套执行：设备树禁用 Linux 对应控制器并处理消费者 → 核对 pinctrl、clock/reset、IRQ、DMA/IOMMU 与共用寄存器位 → UP 驱动初始化和异常退出 → 外部非执行器对端收发及单边重启测试 → 回归 ETH1、按键、DI/DO、系统电源/时钟。不得只在运行时手工 unbind Linux 驱动就宣称物理直驱完成。当前板卡仍保持上述 Linux 绑定，尚未进行 DT 移交。

## 2026-10-09 临时移交窗口：自主配置与 IRQ

CAN1/FD1、CAN3/FD3 的自主配置/IRQ 切片已通过，表中持久所有者不变。
Linux 解绑后先故意关闭 own gate、保持 own reset、把 baud divider 置为 /16；
UP1/UP2 直接恢复各自 gate/reset/divider=/4 并写入 mux，CAN baudclk=297 MHz。
只修改 RK3572 位级字段，不改 GPLL/CPLL/父级总线或其他 CAN 位。
UP1 的 INTID185 实测路由 `0x10`、MPIDR=`0x100`，UP2 的 INTID187 路由
`0x20`、MPIDR=`0x101`；RX FIFO 和 TX 完成由本核 ISR 处理，Linux 不转发帧。

最终固件三轮每路 TX/RX=10000/10000、TXIRQ/RXIRQ=10000/10000，错误计数为 0，
覆盖 Linux 四个低优先级 CPU worker 和两种停止顺序。退出时 UP 先自行禁用 IRQ、
清 pending 并恢复 target/priority，宿主在 CPU4/5 OFF 后读到两个 SPI disabled、
pending/active=0、target=1，才恢复 own CRU/IOC 状态并重绑 Linux。
最终原两实例 Offline、四路 CAN DOWN、micad PID311/active/NRestarts=0、ETH1 正常。
详细地址、原始日志、固件/复建 hash 见 [实机记录](../tests/board/can-irq-20261009/README.md)。

尚未从未知 pinmux/冷启动起步，未持久禁用 Linux CAN 节点；FD2/FD4、
硬实时数据及 UART/SARADC/GMAC1 移交也未完成。最小 MMU 页减少误访问面，
但 CRU/GIC 共享页没有硬件位级防火墙，不能将该切片说成完全硬隔离。
